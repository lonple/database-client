I/O 多路复用 · 监听流程全图解

select / poll / epoll 到底是怎么“监听”的？
一句话：select/poll 是进程亲自睡在每个 socket 的等待队列上；epoll 是回调睡在每个 socket 的等待队列上，进程只睡在 epoll 实例上。

起点 / 准备 判断分支 内核事件 就绪 / 通知 等待队列 / 回调 用户态 / 内核态 常规处理

1总览：从注册到处理

整个多路复用的生命周期，可以概括为 5 个阶段：准备 → 调用等待 → 事件到达 → 被唤醒 → 处理业务。

5等待队列到底是什么？

等待队列（wait queue）是 Linux 内核最基础的结构之一，本质就是一个「通知名单」：谁在等这个事件、事件来了怎么通知他。

// 队列头：挂在 socket 上 struct wait_queue_head { spinlock_t lock; // 保护队列的锁 struct list_head head; // 链表头 }; // 队列节点：每个“等待者”对应一个节点 struct wait_queue_entry { unsigned int flags; void *private; // ← 通知谁 wait_queue_func_t func; // ← 怎么通知（函数指针） struct list_head entry; // 链表节点 };
private：通知谁。可以指向进程，也可以指向一个 epitem。
func：怎么通知。是一个函数指针，wake_up 时挨个调用。
本质：等待队列 = 链表 + 锁，每个节点自带“通知谁 + 怎么通知”。
每个 socket 都有一个：挂在 struct sock 里，叫 sk_wq。

socket 内部的等待队列结构示意：

┌─────────────────────────────────────────────────┐ │ socket │ │ │ │ 接收缓冲区 ← 有数据 = 可读 │ 发送缓冲区 ← 有空间 = 可写 │ │ 等待队列（一个链表） │ ├── 节点A: private=进程P, func=autoremove_wake_function │ └── 节点B: private=epitem, func=ep_poll_callback └─────────────────────────────────────────────────┘

硬中断只做最少的事：记录 + 触发软中断，然后马上返回。
协议栈在软中断里跑：数据包一层层解析，最后放进 socket 接收缓冲区。
sk_data_ready 是函数指针：socket 初始化时指向 sock_def_readable。
wake_up 是回调的源头：遍历等待队列，调用每个节点的 func。

关键代码路径（简化）：

// 协议栈收到数据后，放入 socket 缓冲区，然后调用：
sk->sk_data_ready(sk);   // 函数指针，指向 sock_def_readable

// sock_def_readable 核心动作：
void sock_def_readable(struct sock *sk)
{
    wake_up_interruptible_sync_poll(
        &sk->sk_wq->wait,   // ← socket 的等待队列
        ...
    );
}

// wake_up 系列函数做的事：遍历等待队列，调用每个节点的 func
void __wake_up_common(struct wait_queue_head *wq_head, ...)
{
    struct wait_queue_entry *curr;
    list_for_each_entry(curr, &wq_head->head, entry) {
        curr->func(curr, ...);   // ← 回调就是在这里被调用的
    }
}
所谓回调：就是提前存在等待队列节点里的一个函数指针。
所谓唤醒：就是 wake_up 遍历链表，挨个调用这些函数指针。

10用户态 vs 内核态：数据到底在哪？

理解数据分布，是理解 select/poll 和 epoll 差异的基础。用户态和内核态是两块独立内存，不能直接共享，必须靠 copy_from_user / copy_to_user 拷贝。

🧑 用户态（你的程序）

  • fd 编号：3、4、5 这样的整数
  • fd 集合：select 的 fd_set、poll 的 pollfd[]
  • epoll 的 epfd：epoll 实例的 fd 编号
  • epoll_event ev：注册时传的事件信息
  • events[] 输出数组：epoll_wait 的结果写在这里

⚙️ 内核态（内核自己）

  • 进程 fd 表：fd → struct file 的映射
  • struct file / struct socket / struct sock
  • 接收缓冲区 / 发送缓冲区
  • socket 等待队列：挂等待者节点
  • TCP 哈希表：四元组 → struct sock
  • eventpoll：红黑树 + 就绪链表
  • epitem：每个注册的 fd 对应一个

fd 与内核对象的关系：

用户态 内核态 fd = 3 ──────────────► 进程 fd 表 └── 3 → struct file → struct socket → struct sock ├── 接收缓冲区 ├── 发送缓冲区 └── 等待队列 ├── 进程 P └── epitem
fd 编号：用户态变量，只是门牌号。
fd 表：内核里，每个进程一份。
真正对象：struct socket / struct sock 在内核态。
等待队列：挂在 struct sock 上，不在 fd 上。

原因 1：无状态
select/poll 没有“注册”概念，fd 集合是每次调用临时传入的。调用结束内核就忘了，下次还得重传、重遍历。
原因 2：唤醒不带来源
select/poll 挂在 socket 等待队列上的节点，private 是进程，func 只是 autoremove_wake_function。它只把进程设为可运行，不携带是哪个 fd 就绪的信息。进程醒来后只能自己找。
原因 3：没有就绪链表
epoll 有专门的就绪链表记录“谁就绪了”，回调直接写进去。select/poll 没有这个东西，事件发生时没人帮忙记录，只能靠进程醒来后遍历。

用生活比喻：

📞 select/poll

  • 你在一栋楼里等快递，100 个房间门口都贴了你的电话
  • 哪个房间有快递就打电话叫你
  • 但对方只说“有你的快递”，不说哪个房间
  • 你只能一间一间敲门问：“是我的吗？”

🔔 epoll

  • 你给每个房间装了门铃，门铃连着“待处理篮子”
  • 哪个房间有快递，门铃一响自动把房间号写进篮子
  • 你醒来后直接看篮子
  • 不用敲门，不用遍历

14红黑树 vs 就绪链表：各自干什么？

很多人以为“事件发生时去红黑树查找 fd”，这是错的。红黑树管理注册关系，就绪链表记录就绪状态，回调直接通过 private 拿到 epitem，根本不查红黑树。

操作红黑树就绪链表
epoll_ctl ADD插入 epitem—
epoll_ctl DEL移除 epitem—
事件发生不查回调把 epitem 加入链表
epoll_wait不查直接读链表，取走事件
红黑树：管理“我关心哪些 fd”，只在 epoll_ctl 时用。
就绪链表：记录“哪些 fd 已经就绪”，事件发生时由回调写入。
关键：回调不需要查红黑树，它通过 private 直接拿到 epitem。
epoll_wait：直接读就绪链表，O(就绪数)，不遍历全部 fd。

事件发生时的真实路径：

事件发生 ↓ wake_up 遍历 socket 等待队列 ↓ 调用 ep_poll_callback ↓ 回调通过 private 直接拿到 epitem ← 不查红黑树！ ↓ 把 epitem 加入 epfd 的就绪链表 ↓ 唤醒 epoll_wait 进程 ↓ epoll_wait 直接读就绪链表，返回事件

15常见误区纠正

这些是最容易搞混的地方，单独列出来对照。

❌ 误区 1：事件发生时才把回调挂到等待队列
✅ 正确：epoll_ctl 注册时，回调 ep_poll_callback 就已经挂到 socket 的等待队列上了。事件发生时只是 wake_up 调用这个已经挂好的回调。
❌ 误区 2：回调把自己加入等待队列
✅ 正确：回调做的是把 fd 加入 epoll 实例的「就绪链表」，不是加入等待队列。等待队列是「谁在等」，就绪链表是「谁已经好了」。
❌ 误区 3：epoll_wait 是异步通知，不用循环
✅ 正确：epoll_wait 是同步阻塞等待，必须循环调用。内核内部的回调只是把你唤醒，取事件还得你主动调 epoll_wait。
❌ 误区 4：fd 是 socket 本身
✅ 正确：fd 是进程访问 socket 的编号（句柄），只在当前进程内有意义。内核里 fd → struct file → struct socket → struct sock，才是真正的对象。
❌ 误区 5：网卡收数据时通过 fd 找 socket
✅ 正确：网卡收数据时内核用「四元组」查 TCP 哈希表找到 struct sock，跟 fd 无关。fd 是进程视角，四元组是网络栈视角。
❌ 误区 6：等待队列挂在 fd 上
✅ 正确：等待队列挂在 struct sock 上，不在 fd 上。fd 只是一个编号，本身没有等待队列。
❌ 误区 7：select/poll 返回后，fd 集合还在内核
✅ 正确：select/poll 的 fd 集合是临时副本，返回后就释放了。等待队列上的节点也会被移除。下次调用还得重新传、重新挂。
❌ 误区 8：epoll 事件发生时去红黑树查找
✅ 正确：回调通过 private 直接拿到 epitem，不查红黑树。红黑树只在 epoll_ctl 注册/删除时用。

16代码串起来看

从创建 epoll 到事件循环，完整代码结构。

// 1. 创建 epoll 实例，返回 epfd（它本身也是一个 fd）
int epfd = epoll_create1(0);        // 比如 epfd = 5

// 2. 创建 socket，返回 sockfd
int sockfd = socket(AF_INET, SOCK_STREAM, 0);  // 比如 sockfd = 3

// 3. 把 sockfd 注册到 epfd，关心「可读」事件
//    此时内核会：sockfd 加入红黑树 + 向 sockfd 等待队列注册 ep_poll_callback
struct epoll_event ev;
ev.events = EPOLLIN;
ev.data.fd = sockfd;
epoll_ctl(epfd, EPOLL_CTL_ADD, sockfd, &ev);

// 4. 事件循环：epoll_wait 是同步阻塞等待，必须循环调用
struct epoll_event events[10];
while (1) {
    // 有就绪事件 → 返回 n > 0；超时 → 返回 0；出错 → 返回 -1
    int n = epoll_wait(epfd, events, 10, -1);

    for (int i = 0; i < n; i++) {
        int fd = events[i].data.fd;
        read(fd, buf, sizeof(buf));   // 处理就绪 fd
    }
}
epfd：epoll 实例的 fd，代表内核里的 eventpoll 对象。
sockfd：被监听的 socket fd。
epoll_ctl：把 sockfd 登记到 epfd，同时挂好回调。
epoll_wait：循环调用，主动去取就绪事件。

epoll_wait：同步阻塞，必须循环调用，不是异步通知。
