智能问数：架构 & 业务流程（小白版）

一句话：你用自然语言提问 → 系统帮你找表、想 SQL、生成「数据流」工作流 → 你点执行后去数据库里算出结果。 下面两张图：左边是「谁干啥」，右边是「从聊天到生成 SQL」怎么一步步走。

小白记住 3 条就够：
1）大模型不能随便执行 SQL，只能通过「已声明工具」看目录、画像；真正跑库是服务端 Runner。
2）画布上的 SELECT 是「算什么」；执行时会包成 CREATE TABLE … AS SELECT 落到工作连接。
3）平台库 askdata 存配置与过程；业务数据仍在你的来源库。

② 业务流程：对话里智能问数 → 生成 SQL

从你按下「发送」开始，到屏幕上出现可保存的工作流草稿为止（还没点「执行」）。

1
你输入自然语言

例如：「近 12 个月各部门人均考勤工时和人均报销，只要在职员工。」

2
前端发给问数服务

经 Gateway 带上登录态；右侧「业务工作日志」开始刷：收到消息、开始处理…

3
搜集上下文 · 搜数据目录

search_catalog 在工程「来源连接」里按关键字找可能相关的表（如员工、考勤、报销）。

4
大模型路由：这题算哪一类？

只输出一类意图，决定后面走哪条路（不是直接写最终 SQL）。

A
CHAT 闲聊

「你好」之类 → 普通回复，不弹确认卡、不生成工作流。

B
HITL 缺信息

要查数但缺表名/口径 → 让你确认后再继续。

C
QUERY / GOVERN

简单问数或复杂清洗多表 → 进入生成草稿。

↓ 下面只展开「C：要生成 SQL / 工作流」的路径

5
多轮 Tool：模型自己决定要不要深挖

describe_table看列结构
get_column_profile需要时再统计枚举（如 active / resigned）
模型判断「要不要调」——不是每列都画像。

6
产出工作流 JSON（节点 = 数据步骤）

每个节点是一段 SELECT：GOVERN=清洗后落临时表；末节点 QUERY=最终结果。
下游引用上游用 n1 / __node_n1__，执行时服务端改成真实临时表名。

7
校验 / 修复（可 EXPLAIN）

服务端检查 SQL 是否可读、能否通过解释计划；失败则让模型小修几轮。

8
回到对话：可保存的工作流卡片

你看到助手回复 +「保存到工程 / 保存并执行」。
保存后左侧出现工作流；画布是上下数据流：节点只写「在产什么数据」，点开才看 SQL。

9
（可选）你点执行 → 才真正跑库

Runner 在工作连接上：CREATE TABLE askdata_tmp_* AS … → 最终 askdata_rst_* → 底部「结果」Tab。
这不是生成阶段；生成只负责把「菜谱」写好。

和「直接让 AI 写一句 SQL」的差别：
问数把问题拆成可复跑的数据流节点，中间结果进工作库，可停止、可看日志、可审计；碰库永远走 sqlwork，身份与权限不丢。
