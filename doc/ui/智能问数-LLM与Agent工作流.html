LLM · Tool · LangChain · LangGraph · Deep Agents

专讲「脑子里几块积木怎么配合」。记住一句口诀： LangGraph 管大流程，Deep Agents 管某一站里的多轮工具，LLM 出主意，Tool 干实事，LangChain 是底层协议与依赖。

① 五个角色是啥 ② 谁调用谁 ③ LangGraph 总图 ④ Deep Agents 小环 ⑤ 一次问数时序 业务架构小白版

① 五个角色，人话版

先对号入座，别被名词吓到。

LangChain
生态与通用能力：消息格式、工具 JSON Schema 等。本项目依赖 langchain-core，不单独「跑一套 LangChain Agent」。
LangGraph
总导演：把「搜集 → 路由 → 闲聊/确认/治理/生成 → 校验 → 呈现」画成一张状态图，按条件走边。
Deep Agents（风格）
某一站里的「小导演」：允许多轮 tool_call，模型自己决定要不要继续探测，直到吐出工作流 JSON。
LLM 大模型
只会两种回复：① 纯文本（闲聊 / 最终 JSON）；② tool_calls（点名要调哪个 Tool）。
Tool（声明制）
白名单能力：搜目录、看表结构、列画像/枚举、EXPLAIN… 经 ToolGateway 执行，再调 sqlwork。
和开源「DeepAgents 产品」的关系： 我们实现的是同款交互模式（多轮 tool_call + 强制作用域），代码在 tool_agent.py / deep_govern.py，挂在 LangGraph 的 GOVERN / QUERY 生成节点上。

③ LangGraph：这一次请求的总流程

绿色框 = 图节点；黄框 = Deep Agents 嵌入点；蓝框 = 结束回用户。

1
gather_context

服务端直接调 Tool：search_catalog，把可见表塞进 state（不一定经 LLM）。

2
router · 调 LLM（无 tools）

只输出 JSON：CHAT / QUERY / GOVERN / HITL。闲聊不会误进确认卡。

A
chat_reply

LLM 纯文本闲聊

B
hitl

等人确认，再续跑

C
build_workflow

QUERY · Deep 环

D
govern_plan

GOVERN · Deep 环

3
verify（C/D 之后）

对草稿节点 SQL 做校验/修复，内部可 EXPLAIN，不依赖模型自己去 execute。

4
present

写回会话消息：回复文案 + 草稿卡片（保存 / 保存并执行）。

要点：LangGraph 负责「整段旅程走哪条路」；只有 C/D 两站打开工具箱让模型多轮探索。用户点「执行」不在这张图里——那是外面的 WorkflowRunner。

④ Deep Agents 小环：模型 ↔ Tool 怎么转

发生在 build / govern 节点内部。步数有上限（如 llm_max_tool_rounds / deep_agent_max_steps）。

多轮直到模型不再调用工具
① LLM
看 messages + tools 声明
↓ 若返回 tool_calls
② ToolGateway
