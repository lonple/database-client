## 1. 定位与边界

**做：** 工程（工作连接）、Chat/工作流、执行停止、会话日志、结果弹窗、临时表与结果落库、**已声明 Tool 面（禁模型直调 meta/execute）**、LLM 运行监控、HITL、LangGraph ± Deep Agents。

**不做：** 导出/带到工作台、画布 EXPLAIN、无人自动跑流、给模型开放通用 sqlwork HTTP/SQL、默认全量 Prompt 外传 SaaS、监控失败阻断主流程。

## 3.1 平台库（PostgreSQL · schema `askdata`）

与平台其它服务一致：**共用 PostgreSQL 实例，单独创建 schema**：

```sql
CREATE SCHEMA IF NOT EXISTS askdata;
```

- 问数全部**平台侧**表（工程、会话、工作流、run、llm_span 等）建在 `askdata.*`。  
- 迁移：Flyway / Alembic 等，`search_path` 或显式 `askdata.` 前缀；启动前确保 schema 存在。  
- **区分**：工程「工作连接」上的临时表/结果表在**目标库**（经 sqlwork），不在平台 schema `askdata`。

## 5. Tools 与 sqlwork（实现方案）

### 5.0 强制：只走已声明 Tool（禁止模型直调 meta/execute）

| 规则 | 说明 |
|---|---|
| **声明制** | askdata 内维护 **Tool 注册表**（名称、JSON Schema 入参、描述、是否注册条件如 residency）；LangGraph / Deep Agents **仅**绑定注册表中的 Tool |
| **禁止直调** | 大模型**不得**获得 `SqlworkClient`、任意 URL、或「调用 /meta、/execute」类通用 Tool；Prompt / function-calling 面不出现 sqlwork 原始 API |
| **唯一出口** | 模型只能 `tool_call(name, args)` → `ToolGateway.invoke` → 具体 Tool 实现内部再调 sqlwork |
| **参数收口** | Tool 实现负责拼装 meta 查询或受控 SQL；模型不能传入任意 SQL 去执行（`explain_sql` / 画像等若需 SQL，须经静态校验 + 白名单模板或仅允许模型产出后由 Verify 路径执行，见下） |
| **启动断言** | 未在注册表的 name 拒绝绑定；cloud 下不注册 `sample_columns` |

```text
LLM（只看见已声明 Tool 名与 schema）
  → tool_call
    → ToolGateway（白名单 + 参数校验 + residency + span）
      → 具体 Tool Handler（askdata 代码）
        → SqlworkClient → /meta/** 或 /execute
```

`WorkflowRunner`（用户点击执行）是**服务端编排**，同样经受控路径调 sqlwork，**不是**模型直接调 execute。

**总原则（其余）：** askdata **不**持目标库连接池；Handler 内调 sqlwork 须转发用户 JWT + `workspaceId` + `connectionId`。

### 5.1 查询元数据（声明的 Tool）

| 声明 Tool 名 | Handler 行为 | 内部调 sqlwork |
|---|---|---|
| `list_connections` | 列空间已授权连接 | `GET /workspaces/{id}/connections` |
| `search_catalog` | 入参：connectionId、keyword、分页等（schema 固定） | `GET /meta/databases\|schemas\|tables` |
| `describe_table` | 入参：connectionId、database、schema、table | `GET /meta/columns`（正式） |

模型**不能**传「path=/meta/tables&…」；只能传业务字段。

### 5.2 探测（声明的 Tool）

| 声明 Tool 名 | Handler 行为 | 约束 |
|---|---|---|
| `get_column_profile` | 入参：表/列定位（可选 `top_n`）；Handler 按模板生成聚合 SQL + 取值频次 SQL，再 `/execute`；返回 `row_count` / `distinct_count` / `null_count` / `enum_like` / `value_counts[{value,count}]`；可走列画像缓存 | 模型不传自由 SQL；**由模型判断是否调用**（仅当 WHERE/分组依赖状态、类型等离散码值时） |
| `sample_columns` | 入参：columns[]、max_rows（有上限） | 仅 local；Handler 拼 SELECT；禁 `*` |

**枚举探测约定：**

1. `describe_table` 只给列结构，**不含**枚举取值。  
2. 需要真实码值时，模型主动调 `get_column_profile`；`enum_like=true` 时 `value_counts` 视为可用枚举；高基数列仅 TopN。  
3. SQL **必须**使用 `value_counts` 中的字面量，禁止用自然语言猜码（如 `active` ≠「在职」）。  
4. QUERY / GOVERN 生成均为多轮 tool_call；不强制每列画像。  
5. 配置：`profile_enum_max_distinct`、`profile_enum_top_n`、`profile_cache_ttl_seconds`。

### 5.3 EXPLAIN（声明的 Tool 或 Verify 内部调用）

| 方式 | 说明 |
|---|---|
| Tool `explain_sql`（可选暴露给模型） | 入参：connectionId + sql；Handler：静态校验 → 包装 EXPLAIN → `/execute`；**拒绝**多语句/写语句 |
| VerifyService（推荐主路径） | 生成闭环内由服务代码调用，**不**依赖模型「自己去调 execute」 |

画布无 EXPLAIN 节点；用户 Run 不经该 Tool。

### 5.4 阶段分工

| 阶段 | 谁调 sqlwork |
|---|---|
| 生成 | **仅**已声明 Tool 的 Handler（或 VerifyService） |
| 用户点执行 | **仅** WorkflowRunner（服务端），按工作流节点 SQL 执行 |
| 停止 | Runner → sqlwork cancel |

### 5.5 sqlwork 待扩展

| 项 | 说明 | 优先级 |
|---|---|---|
| `GET /meta/columns` | 表列结构（方言 SPI） | P0 |
| execute cancel 可用 | 支撑停止与长探测 | P0 |
| 只读意图标记（可选） | 区分探测与写入策略 | P1 |

临时表 / 结果表：`askdata_tmp_*` / `askdata_rst_*`（落**工作连接**目标库）。

工程目录建议：`app/tools/registry.py`（声明）+ `app/tools/handlers/*.py`（实现）+ `app/tools/gateway.py`（唯一分发）。

## 6. LangGraph（生成）

> **范围**：用户发送 Chat 消息后的**生成阶段**（意图路由 → 工作流草稿 → 回写会话）。  
> **不含**：用户点「执行」后的落表调度（见 §7 WorkflowRunner）。

### 6.1 总览

文档早期写成一条直线，易误解为「每请求必经 HITL 且既走 govern 又走 build」。**实现为带条件边的状态机**（`dbc_askdata.graph.generate`）：

```text
gather_context → router
                    ├─ CHAT   → chat_reply ─────────────────────────→ present → END
                    ├─ HITL   → hitl ───────────────────────────────→ present → END
                    ├─ GOVERN → govern_plan → (可选再 HITL) → verify → present → END
                    └─ QUERY  → build_workflow_draft ──────→ verify → present → END
```

口诀：

- **LangGraph**：管整次请求走哪条路（总导演）。
- **Deep Agents 风格环**（`run_tool_agent` / `run_deep_govern`）：嵌在 `govern_plan` / `build_workflow_draft` **内部**，多轮 tool_call；图节点只交接「进环 → 拿草稿」。
- **不是**再挂一套独立 DeepAgents 编排框架；环内仍走自研 ToolGateway + LLM Chat Completions。

### 6.2 节点职责

| 图节点 | 职责 | 典型副作用 |
|---|---|---|
| `gather_context` | 服务端调 `search_catalog`，把可见表摘要写入 state | TOOL span；业务工作日志「检索目录」 |
| `router` | LLM（无 tools）输出 `CHAT\|QUERY\|GOVERN\|HITL` | LLM span；短问候优先 CHAT，避免误 HITL |
| `chat_reply` | 普通沟通纯文本回复 | LLM span；`needs_hitl=false` |
| `hitl` | 信息不足：置待确认文案，等人交互后再续跑 | HITL span；会话出确认卡 |
| `govern_plan` | 复杂清洗/多表：进入 Deep 环，产出 GOVERN+QUERY 节点 JSON | 内层多轮 TOOL/LLM；父 span=`govern_plan` |
| `build_workflow_draft` | 简单问数：进入 Deep 环（可按需 `describe_table` / `get_column_profile`） | 同上；父 span=`build_workflow_draft` |
| `verify` | 对草稿各节点 SQL 校验/修复（可 EXPLAIN，不经模型自由 execute） | TOOL/LLM（修复轮次） |
| `present`（present_save_and_execute_actions） | 组装回复；落 assistant 消息 + 草稿卡片（保存 / 保存并执行） | GRAPH span；前端出卡片 |

Deep 环约束（节选）：

1. LLM 看 `messages` + 已声明 tools（`tool_choice=auto`）。  
2. 若有 `tool_calls` → ToolGateway 校验并强制 `workspaceId`/`connectionId`（及工程来源 database/schema）→ Handler → sqlwork。  
3. 结果以 `role=tool` 写回 messages（截断），再调 LLM；步数受 `llm_max_tool_rounds` / `deep_agent_max_steps` 约束。  
4. 无 `tool_calls` 时解析 `content` 为工作流 JSON；下游引用上游用 `__node_n1__` / `FROM n1`（执行期 Runner 改写为真实临时表 FQN）。

### 6.3 与执行阶段的边界

| 阶段 | 谁驱动 | 产出 |
|---|---|---|
| 生成（本节） | LangGraph ± Deep 环 | 会话消息、草稿/已保存工作流 JSON（节点为 SELECT） |
| 执行（§7） | WorkflowRunner | 工作连接上 `askdata_tmp_*` / `askdata_rst_*`，画布日志与结果 Tab |

大模型**不参与**点「执行」之后的节点调度。

### 6.4 可观测：`ask_llm_span`

各图节点进/出、LLM 调用、Tool 调用写平台表 `askdata.ask_llm_span`（自研 `SpanRecorder`，**非** LangGraph/LangSmith 内置 tracing 主路径）。

| kind | 含义 |
|---|---|
| `GRAPH` | 图节点本身（gather / router / present 等） |
| `LLM` | 一次 Chat Completions |
| `TOOL` | 一次声明 Tool |
| `HITL` | 等待用户确认 |

约定：

- **TraceId 贯通**：请求头 `X-Trace-Id`（Gateway / 前端均可注入）。`dbc-askdata` 中间件 `resolve_trace_id`：合法则沿用（`[A-Za-z0-9._-]{8,64}`），缺省或非法则生成 32 位 hex UUID；写入 `request.state`、所有 `ask_llm_span.trace_id`、下游 sqlwork 请求头、审计事件，并在**响应头**回写；chat / hitl / runs 响应体带 `traceId`。实现：`observability/trace.py`。  
- Deep 环内 TOOL/LLM 的 `parent_span_id` 指向外层图节点（如 `govern_plan`），便于在审计中心「智能问数监控」展开子调用。  
- `residency=cloud`：序列化前剔除 sample / 行级明细；全量 Prompt 默认 `store_prompt=false`。  
- 埋点失败：`log.warn(..., exc_info=True)`，**不**阻断生成主流程。  

选用自研 span 而非默认对接 LangSmith 类 SaaS tracing：数据驻留与样本过滤可控，并对接本产品 Grafana + 审计中心展示面（详见 §7.4）。

### 6.5 实现入口

| 模块 | 路径 |
|---|---|
| 状态图 | `dbc_askdata/graph/generate.py` → `run_generate_graph` |
| Deep 环 | `dbc_askdata/graph/tool_agent.py`、`deep_govern.py` |
| Tool 白名单 | `dbc_askdata/tools/gateway.py` + `registry.py` |
| Span | `dbc_askdata/observability/spans.py` |

### 7.4 大模型运行监控

#### 数据模型 `ask_llm_span`

| 字段 | 说明 |
|---|---|
| id / trace_id / parent_span_id | 关联 Gateway TraceId 与父子 |
| workspace_id / project_id / session_id / run_id / user_id | 业务关联 |
| phase | `generate` \| `execute` |
| kind | `LLM` \| `GRAPH` \| `TOOL` \| `HITL` |
| name | 模型名 / 图节点名 / Tool 名 |
| residency / model | LLM 专用 |
| status | OK \| ERROR \| CANCELLED |
| latency_ms / token_in / token_out | 性能与成本 |
| error_code / error_message | 失败（消息截断、无样本行） |
| payload_meta | JSON：长度、哈希、路由结果等；**禁止** cloud 下 sample rows |
| started_at / finished_at | 时间 |

#### 指标（Prometheus）与展示面

指标名示例：

- `askdata_llm_requests_total{model,residency,status}`
- `askdata_llm_latency_ms_bucket{model}`
- `askdata_llm_tokens_total{direction,model}`
- `askdata_graph_node_total{node,status}`
- `askdata_tool_calls_total{tool,status}`
- `askdata_hitl_wait_ms_sum` / `askdata_runs_in_flight`

**Prometheus 不提供业务 UI。** 展示分两路：

| 通道 | 入口 | 内容 |
|---|---|---|
| **Grafana**（运维） | 运维看板 | 刮取 `/metrics`：QPS、P95、Token、失败率等 |
| **审计中心 → 智能问数监控**（产品） | 顶栏「审计日志」侧栏第三项 | 调 askdata `/admin/llm/summary`、`/spans`；列表/筛选/详情；权限 `audit.askdata.view` |
| 原始 `/metrics` | 仅 Prometheus | 不对业务用户开放 |

审计中心侧栏菜单（定案）：

1. 业务日志  
2. SQL 操作日志  
3. **智能问数监控**（新增）

前端模块：`modules/audit` 下新增视图（或 `modules/askdata` 路由挂到审计布局下，推荐挂审计壳层以统一顶栏/侧栏）。**不**再单独开系统管理下的问数监控入口。

#### 埋点原则

1. 入站 `X-Trace-Id`（或服务端生成）写入本请求全部 span / 审计 / sqlwork 下游头；响应头与业务体回传同一 `traceId`。  
2. 埋点失败：`log.warn("llm span failed", ex)`，不抛给主流程。  
3. `residency=cloud`：序列化前跑过滤器，剔除 sample / 行级明细。  
4. 全量 Prompt 默认 `store_prompt=false`；local 可开调试且须权限。

#### 与审计关系

| 系统 | 记什么 |
|---|---|
| ask_llm_span / metrics | 性能、排障、容量 |
| dbc-audit | 创建工程、执行、停止、保存工作流等业务事实 |

## 12. 实施计划（分步）

依赖：Gateway / usercenter / manage / sqlwork 可联调；平台 PG 可建 schema。

### 第 0 步 · 前置（sqlwork / 平台，可并行）

| # | 任务 | 产出 | 验收 |
