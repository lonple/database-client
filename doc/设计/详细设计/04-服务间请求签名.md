# 详细设计：服务间请求签名（横向）

> **横向详细设计**（跨服务）。应用管理 UI 在 usercenter；密钥签发与代签 API 亦在 usercenter。关联：[01-usercenter详细设计.md](./01-usercenter详细设计.md)、[../架构/01-架构设计.md](../架构/01-架构设计.md)。

> 范围：微服务互调对 **URL + Body** 防篡改与防重放；应用管理；**用户中心统一持有签名私钥并代签**；业务侧同步公钥并本地验签；多实例多 `kid`；密钥轮换。  
> 调用用户中心「申请/代签/心跳/公钥」接口时，用 **mTLS（双向 TLS）** 证明应用身份，**不再使用 clientSecret**。  
> 密钥与证书文件 **不进 Nacos / 不进 Git**。签名私钥后续可对接 KMS。

## 1. 定案摘要

1. **应用管理**：一应用一 `clientId`；为每应用签发 **客户端证书**（CN=`clientId`）。  
2. **调中心鉴权**：mTLS；证书身份映射为 `clientId`。  
3. **业务签名密钥对**：用户中心生成并保管 ECDSA 私钥（KEK 加密）；多实例多 `kid`，按 **instanceId**。  
4. **代签**：业务 **HTTPS + 客户端证书** 调用户中心；中心按字段组串（方案 B）后签名。  
5. **验签**：各服务同步公钥，对业务 `/inner/**` 本地验签 + Redis nonce（业务互调仍可为 HTTP + 应用层签名）。  
6. **用户中心自身**：亦用本应用客户端证书走 HTTPS 代签（本机回环）。  
7. **性能**：接受每次代签打中心。

## 1.1 客户端证书何时签发

| 时机 | 行为 |
| --- | --- |
| 用户中心启动 | 确保 CA、mTLS 服务端证书；为库中**已启用**应用补齐缺失的客户端证书 |
| 应用管理「登记应用」 | **立即**签发该 `clientId` 的客户端证书 |
| 「重签证书」 | 覆盖签发新 p12 |

技术：BouncyCastle 签发；RSA 2048；CN=`clientId`；文件 `secrets/mtls/clients/{clientId}.p12`。  
业务模块**启动时不会向中心申请 mTLS 证书**，只读取已下发的 p12，再 `apply` ECDSA 实例密钥。

## 1.2 多实例：证书 vs 签名密钥

| 材料 | 粒度 | 说明 |
| --- | --- | --- |
| mTLS 客户端证书 | **一应用一把** | 同 `clientId` 多实例共用，仅用于调中心 |
| ECDSA 签名密钥对 | **一实例一对（kid）** | 按 `instanceId` 区分；代签/验签按 kid |

## 2. 两套材料（勿混用）

| 材料 | 用途 |
| --- | --- |
| **客户端证书（mTLS）** | 证明「我是哪个应用」，仅用于访问用户中心密钥/代签 API |
| **ECDSA 签名密钥对** | 对业务 `/inner` 请求代签与对端验签 |

已取消 `clientSecret` 作为调中心凭证。

## 3. 端口与流量

| 端口 | 协议 | 用途 |
| --- | --- | --- |
| `8004` | HTTP | 浏览器/网关：登录、用户管理、应用管理（用户 JWT）等 |
| `8044`（可配） | **HTTPS + 强制客户端证书** | 仅 `/inner/apps/keys/**`（申请/代签/心跳/轮换/拉公钥） |

HTTP 上访问 `/inner/apps/keys/**` 直接拒绝，须走 mTLS 端口。

## 4. 总体流程

```text
① 超管登记应用 → 用户中心签发客户端证书 → 写入 secrets/mtls/clients/{clientId}.p12
② 实例启动（持有该 p12）：
     HTTPS+mTLS → apply { instanceId } → kid
③ 心跳 / 拉公钥：同上，mTLS
④ A 调 B(/inner) 前：
     HTTPS+mTLS → sign { instanceId, method, path, query, ts, nonce, bodyHash }
     ← kid + signature
     A 用签名头发业务请求（HTTP 即可）到 B
⑤ B 本地验签 + Redis nonce
⑥ 轮换：rotate(instanceId) → 新 kid
```

## 5. 签名规范（业务请求）

待签串由**中心**组装：

```text
METHOD + "\n" + PATH + "\n" + CANONICAL_QUERY + "\n" +
TIMESTAMP + "\n" + NONCE + "\n" + BODY_SHA256_HEX
```

业务请求头：`X-Dbc-Client-Id` / `X-Dbc-Key-Id` / `X-Dbc-Timestamp` / `X-Dbc-Nonce` / `X-Dbc-Signature`。  
业务 `/inner/**`（非 keys）验签；`/inner/apps/keys/**` 只做 mTLS，不做业务 ECDSA 验签。

## 6. 证书与 secrets 目录

| 路径 | 说明 |
| --- | --- |
| `secrets/mtls/ca.p12` + `ca.crt` | 本地 CA（用户中心信任与签发） |
| `secrets/mtls/trust.p12` | mTLS 信任库（仅 CA 证书条目，供 Tomcat 校验客户端证书） |
| `secrets/mtls/server.p12` | 用户中心 mTLS 服务端证书 |
| `secrets/mtls/clients/{clientId}.p12` | 应用客户端证书+私钥 |
| `secrets/mtls/clients/{clientId}.pass` | 该 p12 密码 |
| `secrets/svc-kek.txt` | 加密库内 **签名私钥** |
| `secrets/jwt-secret.txt` | 用户 JWT |
| `secrets/{clientId}.instance` | 实例 ID |

证书 CN（或 SAN）必须等于 `clientId`。超管「重新签发证书」覆盖客户端 p12。

## 7. API

mTLS 端口（无 clientSecret 头）：

| 接口 | 说明 |
| --- | --- |
| `POST /inner/apps/keys/apply` | 申请/复用实例密钥 |
| `POST /inner/apps/keys/sign` | 代签 |
| `POST /inner/apps/keys/heartbeat` | 心跳 |
| `POST /inner/apps/keys/rotate` | 轮换 |
| `POST /inner/apps/keys/revoke` | 吊销 kid |
| `GET /inner/apps/keys/public` | 存活公钥 |

身份：从客户端证书解析 `clientId`。  
超管 `/apps/**` 仍在 HTTP + 用户 JWT。

## 8. 数据模型

- `t_usercenter_app`：可保留历史 `secret_cipher` 列但**不再用于鉴权**（新签发以证书为准）。  
- `t_usercenter_app_key`：含 `private_key_cipher`、`instance_id`、`kid` 等。

## 9. 不足与安全

- 出站代签依赖用户中心与 mTLS 端口。  
- 私钥仍集中在中心（可换 KMS）。  
- 客户端 p12 泄露 ≈ 原 clientSecret 泄露 → 立即重签证书并视情况吊销 kid。  
- 本地自建 CA 仅适合开发/内网；生产应换企业 PKI / SPIFFE。

## 10. 与旧方案

clientSecret 调中心 → **mTLS**；中心代签 + 本地验签 + Redis nonce + 心跳轮换保持不变。
