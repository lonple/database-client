# 需求输入 → 分析 → 设计

对照 `doc/ui` 的可点击原型和 `doc/设计` 已定稿。正式文档写入 `doc/`，不写进本 skill 目录。模板见 [需求文档模板.md](需求文档模板.md)、[设计文档模板.md](设计文档模板.md)；原型写法见 [UI原型约定.md](UI原型约定.md)。

未写清拍板项之前，不写表结构、接口和实现步骤。

## 进度

```
- [ ] 0 对齐已有原型、上游文档、知识库
- [ ] 1 需求分析（范围、场景、拍板、验收）
- [ ] 2 设计（有新边界才写架构概要，然后写详细设计）
- [ ] 3 原型与索引、doc/README 登记
```

## 0. 对齐

1. 读 `doc/README.md`，确认顶栏、服务名和文档落点。
2. 读 `doc/ui/index.html` 与本次相关 HTML：页间链接、`.note`、必填项、空态、按钮显隐。
3. 读这些页面文末指向的需求 / 详设，以及它们的上游。已有同题文档则修订并追加修订记录，不另起平行稿。
4. 业务事实先 `search_knowledge`（`productName=dbc产品`，`topK=3`）。无命中写「知识库未命中」，再依据仓库文档。
5. 原型 `.note`、需求拍板、代码三者不一致时，写进「非目标澄清」或「拍板」，不静默选边。

平台硬边界（原型里反复出现，新需求不得悄悄打破）：

- 目标库只经 `dbc-sqlwork`；浏览器与 manage 不直连目标库。
- 服务名 = 目录名 = URL 前缀。
- SQL 工作台、智能问数进入业务前必须先选工作空间。
- 删除须二次确认。顶栏顺序以 `doc/ui/index.html` 与 `doc/README.md` 为准。

## 1. 分析

用 [需求文档模板.md](需求文档模板.md)。从原型而不是从想象填这几项：

| 从原型抽出 | 写入需求的位置 |
| --- | --- |
| 页间 `<a href>` 的点击顺序 | 文首「一句话」主路径 |
| 进入前门槛、顶栏、左栏、右栏、弹窗 | 信息架构 |
| 表单标签、`*`、按钮、禁用态、`.note` | 功能需求与交互表现 |
| 空态、失败文案、谁看不见按钮 | 场景与验收 |
| 页脚指向的既有约束 | 上游；冲突则进拍板 |

每条验收必须能指到一个页面、一种状态或一条 `.note`。Out of Scope 写本期明确不做的事，含易误解项（「生成即执行」一类）。

落盘：`doc/设计/需求/NN-标题.md`（沿用目录最大编号 +1）。在 `doc/README.md` 需求表登记。

## 2. 设计

需求里的拍板表已填，才进入设计。用 [设计文档模板.md](设计文档模板.md)。

- 不新增服务、不新开碰库路径：只写详细设计，文首链接总架构 `doc/设计/架构/01-架构设计.md`。
- 新服务、新 schema、新外部调用：先写 `doc/设计/架构/NN-标题架构概要.md`，再写详细设计。
- 详细设计里每个 API、每种页面区域，对应原型上的一个用户操作或一块界面。
- 路由与 `doc/ui` 文件名、`doc/设计/详细设计/06-前端与界面设计.md` 的路由表一致；有增量就改 06，不维护第二套路由。
- 「做 / 不做」与需求的 In / Out of Scope 同文，不在设计里扩大范围。
- 实施计划每步有可检查的验收，不写空里程碑。

落盘：`doc/设计/详细设计/NN-标题详细设计.md`，必要时加架构概要。两边都在 `doc/README.md` 登记。

## 3. 原型

按 [UI原型约定.md](UI原型约定.md) 新增或修改 `doc/ui/*.html`，并在 `index.html` 加卡片。`.note` 只写已经拍板的约束。产品页与「架构说明页」分开：说明页讲谁调用谁，产品页必须能点击走通主路径。

## 完成前核对

- 一句话主路径能沿原型链接走完。
- 拍板、In/Out、验收、设计「做/不做」四方一致。
- 新页面在 `index.html` 与需求文首 UI 链接中出现。
- 异常与失败在需求场景和详设风险中都有着落，不只有成功路径。
- `doc/README.md` 索引含新文档。
